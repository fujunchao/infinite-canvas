# Canvas Data Structure

## Storage

Canvas projects and My Assets are stored with localForage in the `infinite-canvas` database and `app_state` store. Image blobs use `image_files`; other media blobs use `media_files`. Project JSON stores display URLs, `storageKey`, and metadata rather than large base64 payloads.

## Project

```ts
type CanvasProject = {
  id: string;
  title: string;
  createdAt: string;
  updatedAt: string;
  nodes: CanvasNodeData[];
  connections: CanvasConnection[];
  chatSessions: CanvasAssistantSession[];
  activeChatId: string | null;
  backgroundMode: "lines" | "dots" | "blank";
  viewport: { x: number; y: number; k: number };
};
```

The viewport stores screen translation in `x` and `y`, and scale in `k`.

## Nodes and edges

```ts
type CanvasNodeData = {
  id: string;
  type: "image" | "text" | "config" | "video" | "audio" | "group" | string;
  title: string;
  position: { x: number; y: number };
  width: number;
  height: number;
  metadata?: CanvasNodeMetadata;
};

type CanvasConnection = {
  id: string;
  fromNodeId: string;
  toNodeId: string;
  kind?: "batch";
};

type CanvasNodeImage = {
  id: string;
  status: "idle" | "success" | "loading" | "error";
  errorDetails?: string;
  content: string;
  storageKey?: string;
  naturalWidth: number;
  naturalHeight: number;
  bytes: number;
  mimeType: string;
};

type CanvasImagePlacementRef = {
  batchNodeId: string;
  imageId: string;
};
```

Node positions and sizes use canvas-world coordinates. Edges store endpoint node IDs and an optional kind; their paths are calculated while rendering. `kind: "batch"` identifies a root-to-placement relation rather than a generation reference. Deleting a node removes its connected edges.

Common metadata includes content, prompt, status, generation settings, natural dimensions, `storageKey`, MIME type, and byte size. Image and video `content` values are normally session-scoped `blob:` URLs; `storageKey` is the persistent identity.

## Multi-image resources and placement nodes

Multi-image generation uses a hybrid structure:

- The image root is the authoritative resource owner. Its `metadata.images[]` contains every requested image, per-image generation state, dimensions, MIME type, byte size, and `storageKey`.
- `metadata.primaryImageId` selects the image mirrored into the root-level `content`, `storageKey`, dimensions, MIME type, and byte size. The first successful image becomes primary immediately.
- `metadata.imageBatchExpanded` persists the root's expanded/collapsed state. Its presence also retains batch identity when only one candidate remains; an ordinary single-image result has no such field.
- Every candidate is also represented by a real `CanvasNodeData` placement node. Its persisted metadata contains `imageRef: { batchNodeId, imageId }`, interaction fields such as `freeResize` and `groupId`, and optional per-placement prompt/config overrides; it does not duplicate image content or file metadata.
- Rendering, the side panel, generation inputs, downloads, previews, and image tools resolve a placement's image data from the referenced root at runtime.

Generating three images therefore creates four canvas frames: one resource root and three real placement nodes. The source connects to the root, which has a persisted `kind: "batch"` connection to each placement. Placement nodes have stable IDs and independently persist position and size, so they can be selected, moved, resized, connected, copied, retried, and used through the full image toolbar.

Batch lines share the normal connection selection, deletion and reconnection controls and are stored in `project.connections`. Their geometry follows the nodes, and collapse hides them with the placements. Deleting a line does not detach its placement's `imageRef` or stop linked movement; reopening or expanding the project must not recreate a deleted line. Manually reconnecting the root to its placement restores a batch line without duplicating endpoints. Batch lines are excluded from generation references.

Expansion is saved in the root metadata and restored when reopening the project. Collapsing a batch hides its placement nodes and their edges without deleting either; expanding restores the saved geometry and remaining edges. Moving the root moves every placement by the same delta, including hidden placements. Selecting a placement as primary copies its width, height and `freeResize` setting to the root while preserving the root's top-left position and the placement's geometry. Opening/canceling tools, editing prompts/configuration and deriving new images preserve the original reference. Only replacing the placement's media materializes it as an ordinary node, removes its batch line, and removes the original batch resource when no other placement references it.

Deleting the root deletes its placements. Deleting a placement removes the referenced image resource only after the final placement for that image is removed. When one candidate remains, its batch identity, count control, folding, edges and linked movement remain intact. Deleting the final placement converts the root to an ordinary image while preserving the image it was displaying. Copying or duplicating a root includes its placements, remaining internal connections and expansion state, and remaps both `imageRef.batchNodeId` and connection endpoints. A placement copied alone may continue sharing the original resource and `storageKey`; its batch line is copied only if that line still exists.

Canvas Agent uses the same rules, including primary selection geometry, line deletion/reconnection and single-candidate batches. Root movement shifts placements unless explicitly moved in the same operation batch; prompt/config changes stay on the placement; status and file-metadata corrections update its root resource; replacing content detaches. Snapshots resolve the referenced content, while undo snapshots retain the original storage structure.

Projects saved by the legacy root/child batch structure are normalized when opened. Existing child IDs, geometry, storage metadata, primary selection, expansion state and edges are retained as placement nodes; existing root-to-child lines are marked `kind: "batch"`. Current `images[]` batches missing placement nodes receive deterministic placements. Only batches without a saved `imageBatchExpanded` field receive missing batch lines during first initialization and default to collapsed. Once that field exists, missing lines are treated as intentional deletions and are not recreated. Ordinary single-image results do not gain placement nodes or folding controls.

## Generation, groups and video tasks

`metadata.textCount` independently controls text generation count; multiple text results remain ordinary nodes, not `texts[]` candidates. Groups use `metadata.groupId`; generation flattens direct resource members and excludes a root's primary mirror when the corresponding placement is already a member. The reference bar removes group references as a whole.

Video metadata adds `videoMode`, `videoTaskId`, `videoTaskProvider` (`openai`, `gemini`, or `seedance`) and `videoTaskModel`. Native task identity and the original channel/model are saved before polling so reopening the canvas can query the same task even after changing the next-generation model. Network failures retain identity; confirmed remote task failures clear it. Scripted jobs retain their existing in-memory result path and do not receive this recovery guarantee.

The project store also persists `deletedProjects: { id, deletedAt }[]`. WebDAV carries these as the canvas manifest's `deleted` list; deletion hides an older project copy, while a newer edit can supersede the deletion marker. These records are not node data or an account-based cloud database.

## Assistant sessions

```ts
type CanvasAssistantSession = {
  id: string;
  title: string;
  messages: CanvasAssistantMessage[];
  createdAt: string;
  updatedAt: string;
};
```

Message references and generated images use the same blob-storage rules. They are converted to data URLs temporarily only when an AI endpoint requires base64.

## Media lifecycle

`uploadImage()` accepts Blobs, data URLs and remote URLs, supports cancellation, and decodes the downloaded image before storing it in `image_files`. Successful local storage returns an `image:<id>` key, dimensions and an in-memory object URL; opening a project resolves the key again. A displayable remote image that cannot be fetched may remain URL-only, without a storage key. HTTP failures, timeouts and cancellation do not use this fallback. Enabling the optional local proxy forwards HTTP downloads through the local process; it does not change where projects, keys or blobs are stored.

Cleanup is reference-based. After deleting nodes, canvases, assets, or assistant sessions, the application collects every still-referenced storage key, removes unreferenced blobs, revokes their object URLs, and removes them from the in-memory cache. This prevents deleting a file still shared by another canvas feature.

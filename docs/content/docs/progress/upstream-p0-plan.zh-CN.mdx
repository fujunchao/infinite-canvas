# 上游 P0 修复点采计划

> 状态：**已实施（v0.18.4）**。本文保留实施前的分析与验收口径；实际改动见 CHANGELOG 与 v0.18.4 提交。
>
> 基线：本仓库 `v0.18.3`（`e866dce`），上游 `v0.20.0`（`3a6b64b`）。文中行号以 v0.18.3 为准，实施前请重新定位。

## 一、背景与结论

上游在 v0.18.0 之后发布了两个版本：

- **v0.19.0**（2026-09-16，13 个提交）：WebP 缩略图、图片请求 10 分钟超时、ZCode 插件、hover 按钮、拖拽与连线性能。
- **v0.20.0**（2026-10-10，40 个提交）：模型静默回退修复、画布尺寸测量修复、居中聚焦、元素列表缩略图视图、原地重生成偏好、图片质量五档与分辨率解耦、默认分辨率设置、存储统计降级等。

本仓库与上游在画布多图结构上已经分叉（本仓库是「资源根节点 + 真实放置节点」，上游是「单节点 + 候选卡片」，`project.tsx` 双方相差约 1500 行），**不适合整版合并**。因此只点采 4 个与画布批次架构无关、且在本仓库确实存在问题或缺失的修复。

## 三、总原则与完成定义

1. 最小改动：每项只动必要文件，不顺手重构，不改数据结构，不加数据迁移。
2. 独立可回滚：四项互不依赖，任何一项都可以单独 cherry-pick 或 revert。
3. 不改版本号、不发版；完成后由维护者决定是否发 `v0.18.4`。
4. **完成定义（每项都适用）**：代码改动 + 对应测试 + `bun test` 通过 + `bun run typecheck` 无新增错误 + 手测清单勾选 + 文档草稿更新。
5. 文案中英文同时补齐；新增 i18n 键与上游同名，方便后续同步。

## 四、P0-1 图片请求超时

### 4.1 问题与证据

`web/src/services/api/image.ts` 的所有请求只透传 `AbortSignal`，没有设置 `timeout`。上游渠道长时间不返回时，请求一直挂起，节点停在「生成中」，用户只能手动停止。

本仓库的出网调用盘点（只列与本次相关部分）：

| # | 调用 | 位置 | 传输 | 现有超时 | 本计划 |
| --- | --- | --- | --- | --- | --- |
| 1 | 文生图 `/images/generations` | `image.ts:745` | axios | 无 | **加 10 分钟** |
| 2 | Ark 编辑 `/images/generations`（fork 独有） | `image.ts:811` | axios | 无 | **加 10 分钟** |
| 3 | 图生图 / 蒙版 `/images/edits` | `image.ts:862` | axios | 无 | **加 10 分钟** |
| 4 | Gemini 生图 `:generateContent` | `image.ts:684` | axios | 无 | **加 10 分钟** |
| 5 | 流式文本 `/responses` | `image.ts:490` | fetch | 无 | 不做（见 4.5） |
| 6 | 流式文本 Gemini SSE | `image.ts:597` | fetch | 无 | 不做（见 4.5） |
| 7 | 模型列表 `GET /models` | `image.ts:911`、`:918` | axios | 无 | 不做（见 4.5） |
| 8 | 自定义脚本通道 | `model-plugin.ts:50`、`:71` | axios | 无 | 不做（见 4.5） |

参考：图片下载与解码已有超时（`image-storage.ts:20-22`，10 分钟 / 10 秒），本次的超时值与之对齐。

### 4.2 上游做法与 axios 语义

`f84f3ff` 的做法：新增 `IMAGE_REQUEST_TIMEOUT_MS = 10 * 60_000`，给三处 axios 加 `timeout`，并在 `readAxiosError` 里把超时映射成 `apiErrors.imageTimeout`。

需要理解的 axios 1.16 行为：

- 浏览器 XHR 适配器把 `timeout` 设为整请求总时长（send → readyState=4），包含同源排队、上传、服务端等待与响应体下载，不是「首字节前」。
- 超时默认产生 `ECONNABORTED`（`transitional.clarifyTimeoutError` 未开启时不会是 `ETIMEDOUT`）。
- `signal` 取消走另一条路，产生 `CanceledError`（`ERR_CANCELED`），`axios.isCancel()` 为真。
- 因此 **`isCancel` 判断必须排在超时判断之前**，否则用户点「停止」会显示成「请求超时」。

### 4.3 实施方案

`image.ts` 常量区（`IMAGE_OUTPUT_FORMAT` 之后）新增：

```ts
// 与 image-storage 的下载/解码超时同级：接口挂起时节点不会一直停在生成中。
const IMAGE_REQUEST_TIMEOUT_MS = 10 * 60_000;
```

四处 axios 增加 `timeout`（与现有 `signal` 同对象）：

| 位置 | 改动 |
| --- | --- |
| `image.ts:690` | `{ headers: geminiHeaders(config), signal: options?.signal, timeout: IMAGE_REQUEST_TIMEOUT_MS }` |
| `image.ts:758-761` | 选项对象追加 `timeout: IMAGE_REQUEST_TIMEOUT_MS` |
| `image.ts:824-827` | 同上（Ark 分支，上游没有，本仓库自行补） |
| `image.ts:862` | 单行选项追加 `timeout: IMAGE_REQUEST_TIMEOUT_MS` |

错误映射（`image.ts:299-314` 的 `readAxiosError`）：

```ts
if (axios.isCancel(error)) return apiText("requestCanceled");
if (axios.isAxiosError(error) && (error.code === "ECONNABORTED" || error.code === "ETIMEDOUT")) {
    return apiText("imageTimeout");
}
if (axios.isAxiosError(error)) { /* 原逻辑不变 */ }
```

i18n（键名与上游一致）：

- `web/src/i18n/locales/zh-CN.ts` 的 `apiErrors`：`imageTimeout: "生图请求超时，接口长时间没有返回，请稍后重试或更换渠道"`。
- `en-US.ts` 同键：`"The image request timed out. The endpoint did not respond in time; retry later or switch channels."`

### 4.4 行为与错误映射

| 场景 | 现状 | 改后 |
| --- | --- | --- |
| 用户点停止 | `requestCanceled`，节点回 idle | 不变 |
| 10 分钟无响应 | 一直 loading | 节点 error +「生图请求超时」，重试可用 |
| 正常慢请求（4K、多参考图） | 成功 | 成功（10 分钟远大于常规耗时） |
| 浏览器导航导致 XHR abort | 英文 `Request aborted` | 会被映射为超时（稀有，可接受） |

UI 不需要新增：`metadata.errorDetails` 已在节点正文显示（`canvas-node.tsx` 错误态），重试走 `handleRetryNode`；工作台侧 `FailedImageCard` 同理。硬要求是**超时文案不能等于取消文案**，否则会被 `isGenerationCanceled`（`web/src/lib/canvas/canvas-generation-helpers.ts:137`）当成取消吞掉。

### 4.5 明确不在本轮

- **流式请求**（`image.ts:490`、`:597`）：fetch 没有 timeout，给整条流设总时长会误杀长文本/长思考。要做只能做「响应头前 10 分钟」guard，且超时必须抛非 `AbortError` 的命名错误（否则被 `isGenerationCanceled` 吞掉导致节点永久 loading）。风险与收益不匹配，列为后续 P1-1。
- **视频创建与轮询**：创建请求正常 1~3 秒，不应共用 10 分钟；真正的问题是「创建挂起时 120 次轮询上限根本开始不了」，应单独用 60 秒常量，列为 P1-2。
- **模型列表**：`GET /models` 挂起会让选择弹窗一直转圈，建议 30 秒，但属于配置体验，列为 P1-3。
- **自定义脚本通道**：脚本可自设 timeout，且影响四种能力，需单独回归，列为 P1-4。

### 4.6 风险

1. 10 分钟偏长：最坏一张图 20 分钟（生成 10 + 下载 10）。可接受——用户随时能停止，本次目标是「防挂死」而非「提速」。
2. 预算包含上传与同源排队：编辑请求把多张参考图放进 FormData，慢上行会吃掉部分预算；gemini 并发 count 次时后发请求先耗排队时间。
3. 本地代理链路没有第二个超时（`canvas-proxy` 无业务超时、nginx 只托管静态文件），不会叠加。
4. 上线后可按 `errorDetails` 中 `imageTimeout` 的占比观察，必要时提高阈值；常量集中一处，调整成本低。

### 4.7 测试与验收

自动化：超时时长没有可注入时钟，且 `image.ts` 依赖链较重（localforage/i18n），不建议为它引入 axios adapter 替换；以手测为准。

手测（临时把常量改成 3000ms 验证，验完还原）：

1. 把渠道 Base URL 指向一个「接受连接但不返回」的本地地址，触发一次生图。
2. 3 秒后节点应变为错误态、显示「生图请求超时」、重试按钮可用、`message.error` 只弹一次。
3. 在 3 秒内点停止，必须显示「请求已取消」并回到 idle，不能出现超时文案。
4. 正常路径各跑一次：gpt-image 生图、Gemini 生图、带参考图编辑、Ark 编辑、脚本渠道生图。
5. 切到英文界面，确认同一条错误显示英文。
6. 正式验收用 10 分钟常量跑一次慢服务（约 11 分钟），确认链路真实生效。

### 4.8 回滚

只涉及 `image.ts` 与两个 locale 文件，revert 即恢复。

## 五、P0-2 画布尺寸测量失效

### 5.1 根因

`web/src/pages/canvas/project.tsx:607-624` 的尺寸测量 `useEffect` 使用空依赖数组：

- 组件首次挂载时 `projectLoaded = false`，`:3106` 直接返回 `CanvasRefreshShell`，画布容器 `InfiniteCanvas`（`:3137` 传入 `containerRef`）尚未渲染，`containerRef.current` 为 null。
- effect 里 `:609` 早退，`ResizeObserver` 从未创建；空依赖又让它永远不会重跑。
- 结果是 `size` 永久停留在 `:251` 的默认值 `{ width: 1200, height: 720 }`，直到刷新页面。
- 全仓只有这一处观察画布尺寸（其余 3 处 `ResizeObserver` 都不是画布容器），没有任何补偿路径。

`:212` 的 `didInitialCenterRef` 与 `:614-617` 的首次居中因此是**死代码**：当前版本「初始居中」根本不存在，初始视口唯一来源是 `:507` 的项目恢复。

### 5.2 影响面

| 位置 | 用途 | 错值后果 |
| --- | --- | --- |
| `:638-641` `getCanvasCenter` | 新节点落点 | 偏左上 |
| `:1174-1177` `resetViewport` | 重置视图 | 世界原点不在画布中心 |
| `:1179-1208` `focusNode` | 侧栏点击聚焦 | 节点不居中，缩放比例也按错尺寸算 |
| `:1212-1223` `setZoomScale` | 以容器中心缩放 | 缩放锚点漂移 |
| `:3314` 小地图 | 视口框与点击定位 | 比例错误、点击跳转不居中 |
| `:2164-2169`、`:2950-3021` | 导入与助手插入落点 | 偏移 |
| `:747-758` 视口裁剪 | 只渲染可见节点 | **不受影响**：优先用实时 `getBoundingClientRect` |

### 5.3 上游补丁与「必须成对」的反证

`99bb4b3` 改了一个文件（+2/−6）：

1. 删除 `didInitialCenterRef` 声明。
2. effect 首行加 `if (!projectLoaded) return;`。
3. 删除 `updateSize` 里的首次居中分支。
4. 依赖由 `[]` 改为 `[projectLoaded]`。

**只加依赖不删居中会怎样**：项目恢复完成（`setViewport(project.viewport)` 之后）effect 重跑，居中分支会把视口覆盖成容器中心；紧接着 `:581-591` 的 500ms 视口保存定时器把被覆盖的值写回项目——**每次打开项目，平移和缩放都会被重置并持久化**，属于数据级回归。所以这两步必须同一次提交完成。

### 5.4 实施方案

只改 `web/src/pages/canvas/project.tsx`：

1. 删除 `:212` 的 `const didInitialCenterRef = useRef(false);`。
2. `:607` 的 effect 首行增加 `if (!projectLoaded) return;`。
3. 删除 `:614-617` 的首次居中代码块。
4. `:624` 的依赖数组改为 `[projectLoaded]`。

改后形态：

```ts
useEffect(() => {
    if (!projectLoaded) return;
    const el = containerRef.current;
    if (!el) return;
    const updateSize = () => {
        const rect = el.getBoundingClientRect();
        setSize({ width: rect.width, height: rect.height });
    };
    updateSize();
    const resizeObserver = new ResizeObserver(updateSize);
    resizeObserver.observe(el);
    return () => resizeObserver.disconnect();
}, [projectLoaded]);
```

### 5.5 时序验证（为什么不会互相覆盖）

1. 首次渲染：`projectLoaded = false`，effect 直接返回，不注册观察器。
2. 项目恢复：`restore()` 写入节点、连线、`viewport`（`:507`），最后 `setProjectLoaded(true)`（`:522`）。
3. 重新渲染：容器挂载，`containerRef` 指向真实元素。
4. effect 因依赖变化执行：量出真实尺寸并 `setSize`，**不再写 viewport**。
5. `setSize` 触发重渲染：`viewport` 未变，effect 不重跑，观察器保持连接。
6. 切换项目：`projectLoaded` 先 false 再 true，cleanup 断开旧观察器、重新测量。
7. 窗口 resize、侧栏展开收起（500ms 宽度动画）、Agent 面板开关：均由 `ResizeObserver` 触发更新。

结论：`size` 只由测量 effect 写，`viewport` 只由项目恢复与用户交互写，两者解耦。

### 5.6 初始视口决策（D1）

当前 bug 状态下，新建项目视口就是 `{x:0,y:0,k:1}`（`use-canvas-store.ts:42,89`），「首次居中」从未执行。修复后行为完全一致：

- 已有项目：严格恢复保存的视口。
- 新建空项目：视口 `{0,0,1}`，第一个节点仍落在容器中心（`getCanvasCenter` 用实时 rect）。

因此本计划**不改初始视口行为**。若产品希望「新空项目进入时原点居中」，应另立需求：给项目增加 `viewportInitialized` 标记，测量完成后只对未初始化项目居中并写回——不要在组件里恢复 ref 居中，否则会被项目恢复覆盖并持久化。

### 5.7 可选取整加固（建议单独提交）

面板动画期间 `ResizeObserver` 每帧回调会 `setSize`，500ms 约 30 次整页重渲染。建议在 `updateSize` 内取整并做等值守卫：

```ts
const width = Math.round(rect.width);
const height = Math.round(rect.height);
if (!width || !height) return;
setSize((prev) => (prev.width === width && prev.height === height ? prev : { width, height }));
```

与上游差异隔离，便于后续同步；即使不做也不影响 P0 结论。

### 5.8 风险

| # | 风险 | 结论 |
| --- | --- | --- |
| R1 | 首次测量发生在绘制后的 effect，存在一帧 `size=1200×720` | 无可见影响：变换只用 `viewport`，裁剪优先用实时 rect，小地图默认关闭 |
| R2 | 侧栏入场动画首帧宽度偏小 | 观察器一两帧内纠正；居中已删，偏值不会写进视口 |
| R3 | 面板动画期间频繁 `setSize` | 用 5.7 的取整与等值守卫缓解 |
| R4 | 只加依赖不删居中 | 数据级回归，必须同提交（见 5.3） |
| R5 | StrictMode 双执行 | cleanup 会 disconnect，无泄漏 |
| R6 | 改动 `:2164-2169` 等 4 处 `rect.left + size.width/2` | **不要改**：`size` 修好后自动正确，改了只扩大后续合并冲突面 |

### 5.9 测试与验收

自动化：effect 是否注册无法在 bun（无 DOM/布局）中验证。可选两条路：

- 把视口数学抽成纯函数（`resetViewportFor(size)`、`focusViewportForNode(node,size)`、`zoomAtCenter(viewport,size,scale)`）并补 3~5 个用例，锁住「size 是外部输入」的数学；这属于小重构，建议随 P1 的居中聚焦一起做。
- 或加一条廉价的源码文本断言，检查 effect 片段同时包含 `if (!projectLoaded) return;` 与 `}, [projectLoaded]);`，防止未来被改回去（脆弱，团队可自行取舍）。

手测（建议固定窗口 1440×900，先用 DevTools 记录画布容器真实 rect）：

1. 打开被拖动过视口的项目，刷新后视口与上次一致，不被重置。
2. 点击「重置视图」，世界原点位于画布可视区中心。
3. 侧栏列表点击节点聚焦，节点中心落在可视区中心。
4. 收起/展开侧栏后再聚焦，仍准确（证明尺寸随布局更新）。
5. 打开小地图，视口框比例与真实画布一致；点击角落能定位到对应世界坐标。
6. 缩放滑杆以中心为锚点缩放。
7. 拖拽/粘贴/导入（无目标节点）时新节点出现在画布中心。
8. 窗口 resize 后重复 2、3、6。
9. 新建项目 → 从工具栏添加节点 → 出现在中心。
10. 关闭/打开 Agent 面板后重复 2、3。

## 六、P0-3 模型与渠道被删后静默回退

### 6.1 问题与证据

`web/src/stores/use-config-store.ts` 有两处会「悄悄换成别的模型或渠道」：

- `resolveModelForCapability`（`:180-186`）：当前模型无法解析能力时，依次回落到默认模型与 `defaultConfig` 的硬编码模型。
- `isAiConfigReady`（`:198-200`）：用 `resolveModelChannel` 判断，而 `resolveModelChannel`（`:417-422`）找不到匹配渠道时返回 `channels[0]`。

结果：用户删除渠道或模型后，下一次生成可能被发到第一个渠道，使用用户没有选择的 Key 与 Base URL，界面没有任何提示。

在仓库外用上游测试用例跑本仓库源码（基线 `e866dce`）的实测结果：

- 8 条上游断言里 **3 通过 / 5 失败**，失败项正好是「已删渠道被替换」「删模型后仍能重试」「续查未知渠道」「显式失效默认被替换」「四种能力丢失选择」。

### 6.3 实施方案

本仓库已有 `findChannelModel`（`:163`）与 `modelCapabilityOf`（`:171`），只替换两段逻辑（保留 `ark` 协议分支）：

```ts
// :180
export function resolveModelForCapability(config: AiConfig, currentModel: string | undefined, capability: ModelCapability) {
    const defaultModel = capability === "image" ? config.imageModel : capability === "video" ? config.videoModel : capability === "audio" ? config.audioModel : config.textModel;
    const fallbackModel = capability === "image" ? defaultConfig.imageModel : capability === "video" ? defaultConfig.videoModel : capability === "audio" ? defaultConfig.audioModel : defaultConfig.textModel;
    for (const model of [currentModel, defaultModel]) {
        if (!model) continue;
        const configuredCapability = modelCapabilityOf(config, model);
        // 保留不可用的选择，让 readiness 阻止请求；只有已知能力不匹配时才切换。
        if (!configuredCapability || configuredCapability === capability) return model;
    }
    return fallbackModel;
}

// :198
function isAiConfigReady(config: AiConfig, model: string) {
    const match = findChannelModel(config, model);
    return Boolean(match && match.channel.baseUrl.trim() && match.channel.apiKey.trim());
}
```

另外三处必须一起改：

**改动 3：导出 `findChannelModel`**（`use-config-store.ts:163`）。`function` 改为 `export function`，供服务层与测试复用，无行为变化。

**改动 4：修掉视频重试的死循环**（`project.tsx:2768`）。`handleRetryNode` 先判断「是否可续查视频任务」，是则直接转入轮询：

```ts
if (hasResumableVideoTask(rawNode)) return pollVideoNodeTask(rawNode);
```

而 `pollVideoNodeTask` 用节点保存的 `videoTaskModel` 重建配置并做 readiness 检查（`project.tsx:366-374`）。readiness 变严后，原渠道被删的节点每次点重试都会：命中续查分支 → 用旧渠道模型判 readiness → 失败 → 打开配置弹窗并返回。用户即使重新选了有效模型，节点里的 `videoTaskModel` 仍是旧渠道，**永远无法重新生成**（该死循环今天已存在于「清空 API Key」场景，严格门控只是扩大触发面）。

建议改法：续查前先判断任务配置是否就绪，不就绪则清掉任务身份、走重新生成。

```ts
if (hasResumableVideoTask(rawNode)) {
    const taskConfig = buildGenerationConfig(effectiveConfig, { ...rawNode, metadata: { ...rawNode.metadata, model: rawNode.metadata?.videoTaskModel } }, "video");
    if (isAiConfigReady(taskConfig, taskConfig.model)) return pollVideoNodeTask(rawNode);
    // 原渠道已不可用：放弃续查，清掉任务身份后走重新生成，避免死循环。
    setNodes((prev) => prev.map((item) => (item.id === rawNode.id
        ? { ...item, metadata: { ...item.metadata, videoTaskId: undefined, videoTaskProvider: undefined, videoTaskModel: undefined } }
        : item)));
    message.warning(t("workbench.modelUnavailable", { model: rawNode.metadata?.videoTaskModel || "" }));
}
```

**改动 5：四处门控补提示**（`project.tsx:2017`、`:2092`、`:2341`、`:2782`）。现在这些分支只调用 `openConfigDialog(true)`，用户看不出原因；改为先 `message.warning` 再开弹窗。工作台（`image/index.tsx`、`video/index.tsx`）与插件宿主已有提示，只按原因分流文案即可。

## 七、P0-4 本地存储统计降级

### 7.1 问题

`web/src/services/local-storage-usage.ts:5-8` 直接调用 `navigator.storage.estimate()` 并断言 `usage`、`quota` 存在；`config-local-storage.tsx:42` 又直接用 `usage.quota` 计算百分比。在无 Storage API、权限受限或实现异常的页面（部分内嵌 WebView、非安全上下文）会抛错，配置页「本地存储」整块只剩一条错误提示。

### 7.2 实施方案

`local-storage-usage.ts`：

```ts
export type LocalStorageUsage = { usage: number; quota: number | null; contentBytes: number; databases: IndexedDbDatabaseUsage[] };

export async function readLocalStorageUsage(): Promise<LocalStorageUsage> {
    const [estimate, database] = await Promise.all([readStorageEstimate(), readDatabaseUsage("infinite-canvas")]);
    return { usage: estimate?.usage ?? database.bytes, quota: estimate?.quota ?? null, contentBytes: database.bytes, databases: [database] };
}

async function readStorageEstimate() {
    if (typeof navigator === "undefined" || !navigator.storage?.estimate) return null;
    try {
        return await navigator.storage.estimate();
    } catch {
        return null;
    }
}
```

再加两处加固：

```ts
// readDatabaseUsage 首行：无 indexedDB 时返回空统计，不抛错
if (typeof indexedDB === "undefined") return Promise.resolve({ name, version: 0, bytes: 0, stores: [] });
```

并把两个纯函数搬到 service 层导出，便于单测：

- `formatStorageBytes(bytes: number | null)`：`null` 返回「—」，其余逻辑不变。
- `storageQuotaPercent(usage)`：`quota` 为空或 0 时返回 `null`，否则 `Math.min(100, usage / quota * 100)`。

`config-local-storage.tsx` 五处调整：

| 行 | 改动 |
| --- | --- |
| `:42` | `const percent = usage ? storageQuotaPercent(usage) : null;` |
| `:67` | hint 按 `usage.quota` 是否为有效正数，切 `quotaHint` / `quotaUnavailable` |
| `:69-75` | 整条进度条包在 `percent !== null ? (...) : null` 中 |
| `:74` | `percent={percent ?? 0}` |
| `:121-126` | 删除本地 `formatStorageBytes`，改为从 service 导入 |

i18n（键名与上游一致）：`config.localStorage.quotaUnavailable: "当前浏览器不提供配额估算"`。

实测失败模式（基线）：`navigator` 没有 `storage` 时直接 `TypeError`；`estimate()` 抛 `SecurityError` 时原样上抛；`estimate()` 返回 `{}` 时 `usage`/`quota` 都是 `undefined` 且无人处理。`navigator.storage` 属 SecureContext API，本项目用局域网 HTTP 访问部署实例时必然命中；而 IndexedDB 明细本身仍然可用，所以降级方案是「保明细、配额显示未知」。

### 7.3 测试与验收

自动化：新增 `web/tests/local-storage-usage.test.ts`，7 条：

1. `navigator` 无 `storage` → 不抛，`quota === null`，`usage` 回退为 IndexedDB 字节数。
2. `estimate()` 抛 `SecurityError` → 同上。
3. `estimate()` 返回 `{ usage: 123, quota: 456 }` → 原样透出。
4. `estimate()` 返回 `{}` → `usage` 回退、`quota === null`。
5. `indexedDB` 缺失 → 不抛。
6. `formatStorageBytes(null) === "—"`、`1536 → "1.5 KB"`、`0 → "0 B"`。
7. `storageQuotaPercent`：`{usage:50,quota:100} → 50`；`quota:null → null`；`quota:0 → null`（防 `NaN` / `Infinity`）。

做法：stub `globalThis.navigator` 与 `globalThis.indexedDB`，`afterAll` 还原。

手测：

1. 正常 Chrome：显示 IndexedDB 占用、站点占用、配额与进度条，下方按仓库明细完整。

3. 刷新页面恢复：三块指标与进度条正常。

- 复制/粘贴带参考连线。
- 图片质量五档、尺寸与质量解耦、脚本 `resolution` 参数、Gemini `imageSize`。
- 流式请求超时、视频创建/轮询超时、模型列表超时、脚本通道超时（P1-1 ~ P1-4）。
- ZCode 插件支持、pnpm workspace、移除 Ark / Seedance。
